SDLC — Software Development Life Cycle

📄 SDLC (Software Development Life Cycle)

📝 Definición

El SDLC (Ciclo de Vida del Desarrollo de Software) es un marco de trabajo estructurado que describe las fases y etapas por las que pasa un proyecto de software, desde su concepción hasta su retiro.

Proporciona un plan sistemático para desarrollar, mantener y mejorar software de alta calidad, garantizando que se cumplan los requisitos del cliente y los estándares de la organización.

🧠 ¿Qué es?

El SDLC no es una metodología en sí misma (como Agile o Scrum), sino un concepto general que define las etapas que todo proyecto de software debe atravesar.

Cada metodología (Waterfall, Agile, DevOps, etc.) implementa el SDLC de una manera particular, adaptando las fases a su enfoque.

El objetivo del SDLC es estandarizar el proceso de desarrollo de software, reduciendo riesgos, costos y tiempos, y asegurando que el producto final cumpla con las expectativas de los usuarios.

En resumen: El SDLC es el "qué" (las fases que hay que hacer), mientras que las metodologías son el "cómo" (la forma de hacerlas).

🎯 ¿Para qué sirve?

  • Estructurar el desarrollo: Proporciona un camino claro y predecible para el equipo.
  • Reducir riesgos: Permite identificar problemas en etapas tempranas.
  • Controlar costos y tiempos: Al planificar, se evitan desviaciones presupuestarias.
  • Garantizar la calidad: Incluye pruebas y revisiones en todas las fases.
  • Mejorar la comunicación: Establece hitos y entregables claros para todos los stakeholders.
  • Facilitar el mantenimiento: Documenta el software, lo que facilita futuras modificaciones.

⚙️ ¿Cómo funciona? Las 7 Fases del SDLC

Aunque el número de fases puede variar según la fuente, el SDLC clásico consta de 7 etapas:

1️⃣ Planificación (Planning)

  • Qué es: Se define el alcance del proyecto, los objetivos, los recursos necesarios y el presupuesto. Se evalúa la viabilidad del proyecto.
  • Entregables: Documento de viabilidad, plan de proyecto, cronograma preliminar.
  • Preguntas clave: ¿Vale la pena hacer este proyecto? ¿Es viable técnica y económicamente? ¿Cuánto costará y cuánto tiempo tomará?

2️⃣ Análisis de Requisitos (Requirements Analysis)

  • Qué es: Se recopilan y documentan las necesidades y expectativas de los usuarios y stakeholders. Se define qué debe hacer el software, no cómo lo hará.
  • Entregables: Especificación de Requisitos de Software (SRS - Software Requirements Specification), casos de uso, historias de usuario.
  • Preguntas clave: ¿Qué necesita el cliente? ¿Qué funcionalidades debe tener el sistema? ¿Cuáles son las restricciones?

3️⃣ Diseño (Design)

  • Qué es: Se define la arquitectura del software, los componentes, la interfaz de usuario, la base de datos, y cómo interactuarán entre sí. Se pasa del "qué" al "cómo".
  • Entregables: Documento de Diseño del Sistema (SDD - System Design Document), wireframes (diseño de pantallas), diagramas UML, esquema de base de datos.
  • Tipos de diseño:
    • Diseño de Alto Nivel (Arquitectura): Módulos, servidores, plataformas.
    • Diseño de Bajo Nivel (Detallado): Estructura de datos, algoritmos, interfaces.
  • Preguntas clave: ¿Cómo vamos a construir esto? ¿Qué tecnología usaremos? ¿Cómo se verá la interfaz?

4️⃣ Implementación (Implementation / Development)

  • Qué es: La fase de codificación. Los desarrolladores escriben el código fuente según los requisitos y el diseño establecidos.
  • Entregables: Código fuente, builds ejecutables, documentación técnica.
  • Preguntas clave: ¿El código sigue los estándares? ¿Se está desarrollando según lo planeado? ¿Estamos en el cronograma?

5️⃣ Pruebas (Testing)

  • Qué es: Se verifica que el software funciona correctamente, cumple con los requisitos y no tiene errores (bugs). Se realizan diferentes niveles de prueba.
  • Entregables: Plan de pruebas, casos de prueba, informes de errores (issue tracking).
  • Tipos de pruebas:
    • Pruebas Unitarias: Prueban componentes individuales.
    • Pruebas de Integración: Prueban la interacción entre componentes.
    • Pruebas de Sistema: Prueban el sistema completo.
    • Pruebas de Aceptación de Usuario (UAT): Prueban los usuarios finales en un entorno realista.
    • Pruebas de Rendimiento: Evalúan la velocidad y estabilidad bajo carga.
    • Pruebas de Seguridad: Buscan vulnerabilidades.
  • Preguntas clave: ¿El software hace lo que tiene que hacer? ¿Se rompe bajo ciertas condiciones? ¿Es seguro?

6️⃣ Implementación / Despliegue (Deployment)

  • Qué es: Se entrega el software al usuario final. Puede ser una implementación gradual (piloto) o completa (big bang).
  • Entregables: Versión final del software, documentación del usuario, guías de instalación y despliegue.
  • Actividades clave: Migración de datos, configuración de servidores, capacitación de usuarios.
  • Preguntas clave: ¿El software se instala correctamente? ¿Los usuarios saben cómo usarlo?

7️⃣ Mantenimiento (Maintenance)

  • Qué es: Una vez en producción, el software requiere soporte continuo para corregir errores, agregar nuevas funcionalidades y adaptarse a cambios en el entorno (nuevas versiones de sistemas operativos, cambios en la legislación, etc.).
  • Entregables: Parches (patches), nuevas versiones, informes de incidentes.
  • Tipos de mantenimiento:
    • Correctivo: Corregir errores detectados.
    • Adaptativo: Adaptarse a cambios del entorno.
    • Perfectivo: Mejorar el rendimiento o añadir nuevas funcionalidades.
    • Preventivo: Prevenir problemas futuros.
  • Preguntas clave: ¿El software sigue funcionando bien? ¿Necesita actualizaciones? ¿Los usuarios están satisfechos?

📝 Modelos de SDLC (Metodologías)

El SDLC se puede implementar a través de varios modelos o metodologías, cada uno con su propio enfoque y filosofía:

ModeloDescripciónCuándo Usarlo
Waterfall (Cascada)Modelo secuencial donde cada fase debe completarse antes de pasar a la siguiente. No se vuelve atrás.Proyectos pequeños, requisitos estables y bien comprendidos.
Modelo en V (V-Model)Versión del Waterfall con énfasis en las pruebas, donde cada fase de desarrollo tiene una fase de prueba correspondiente.Proyectos donde la calidad y las pruebas son críticas y los requisitos están claros.
Iterativo e IncrementalEl software se construye en incrementos o iteraciones, cada una añadiendo más funcionalidad.Proyectos grandes donde se puede entregar valor en partes (early delivery).
Espiral (Spiral)Combina desarrollo iterativo con análisis de riesgos. Cada ciclo incluye planificación, análisis de riesgos, desarrollo y evaluación.Proyectos de alto riesgo, grandes y complejos (ej: sistemas de defensa, aeroespacial).
Ágil (Agile)Desarrollo iterativo, incremental y flexible. Se centra en la entrega rápida de valor, la colaboración con el cliente y la adaptación al cambio. Frameworks: Scrum, Kanban, XP.La mayoría de los proyectos modernos, especialmente en entornos cambiantes y startups.
DevOpsExtiende Agile integrando desarrollo (Dev) y operaciones (Ops). Enfoque en la automatización, la entrega continua (CI/CD) y la colaboración entre equipos.Proyectos que requieren despliegues frecuentes y alta disponibilidad.
LeanSe centra en eliminar desperdicios y maximizar el valor para el cliente.Proyectos donde la eficiencia y la reducción de costos son críticas.

⚠️ Errores Comunes en el SDLC

ErrorDescripciónConsecuencia
Saltarse la fase de análisisEmpezar a codificar sin comprender bien los requisitos.Se construye lo incorrecto, se desperdicia tiempo y dinero.
Documentación insuficienteNo documentar el diseño, las decisiones y el código.El mantenimiento es difícil y costoso, el conocimiento se pierde.
Ignorar las pruebasRealizar pruebas insuficientes o en las etapas finales.Errores en producción, mala experiencia del usuario.
No involucrar al usuarioDesarrollar sin la participación activa del cliente/usuario.El producto final no satisface las necesidades reales.
No gestionar los riesgosNo identificar y mitigar los riesgos potenciales.El proyecto se desvía, se retrasa o incluso se cancela.
Tecnología inadecuadaElegir una tecnología que no se adapta al problema o al equipo.Dificultades técnicas, bajo rendimiento, alta rotación del equipo.
Metodología equivocadaUsar Waterfall para un proyecto con requisitos cambiantes.Rigidez, incapacidad de adaptarse, producto obsoleto al lanzarlo.

💼 Casos de Uso

SituaciónAplicación
Desarrollo de un nuevo productoUsar Agile (Scrum) para iterar rápidamente y recibir feedback del mercado.
Sistema crítico (banca, salud)Usar V-Model o Espiral, con énfasis en pruebas y validación rigurosa.
Migración a la nubeUsar DevOps (CI/CD) para automatizar la entrega y garantizar la disponibilidad.
Proyecto con requisitos fijos (ej: normativa)Usar Waterfall, donde los requisitos son estables y bien conocidos.

🧠 Analogía

El SDLC es como construir una casa:

  • Planificación: Decides construir una casa, defines el presupuesto y el terreno.
  • Análisis de Requisitos: Hablas con tu familia para saber cuántos baños, habitaciones y qué estilo quieren.
  • Diseño: El arquitecto dibuja los planos.
  • Implementación: Los albañiles construyen la casa siguiendo los planos.
  • Pruebas: Inspeccionas que las tuberías no goteen, que las luces funcionen y que todo esté bien construido.
  • Despliegue: Te mudas a la casa.
  • Mantenimiento: Reparas una gotera, pintas una habitación o remodelas la cocina con el tiempo.

Así como construir una casa sin planos o sin inspecciones sería un desastre, desarrollar software sin un SDLC estructurado llevaría a resultados impredecibles y de baja calidad.

📝 Notas personales

  • No existe el "mejor" modelo de SDLC: Depende del proyecto. Para una startup con un producto nuevo, Agile es ideal. Para un sistema de control de tráfico aéreo, un modelo como Espiral (con mucho análisis de riesgos) es más apropiado.
  • El SDLC no es rígido: Puedes combinar elementos de diferentes modelos. Por ejemplo, usar Agile para el desarrollo pero incorporar fases de análisis de riesgos de Espiral para ciertos módulos críticos.
  • La documentación es clave: A menudo se subestima, pero una buena documentación (de requisitos, de diseño, de usuario) es lo que permite mantener y evolucionar el software a largo plazo.
  • La participación del usuario es crítica: El mayor fracaso en el desarrollo de software no es técnico, sino de entendimiento del cliente. Involucrar al usuario desde la fase de análisis y en las pruebas de aceptación es la mejor inversión para asegurar el éxito.
  • El mantenimiento es la fase más larga: El 80% del costo total de un software ocurre durante la fase de mantenimiento, no durante el desarrollo inicial. Por eso es tan importante la calidad del código y la documentación.
  • DevOps como estándar: En la era de la transformación digital, DevOps se está convirtiendo en el estándar de facto para el SDLC, ya que permite desplegar nuevas versiones de software de manera rápida, segura y continua (CI/CD).
